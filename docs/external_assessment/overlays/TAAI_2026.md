## Why Hardware-Splicer fits unusually well

The 2026 conference theme is:

> **Agentic AI and Physical AI for Cross-Domain Sustainable Innovation**

The CFP explicitly includes:

### Track A — Agentic AI & LLM systems

- autonomous LLM agents;
- tool use / function calling;
- multi-agent orchestration;
- long-horizon planning;
- memory/retrieval;
- **agent evaluation & benchmarks**;
- reasoning/reflection;
- **agent safety & alignment**.

### Track B — Physical & embodied AI

The track covers real-world/embodied AI topics including robotics/manipulation, sim-to-real, vision-language-action systems and human-robot interaction.

### Track D — Sustainable & cross-domain applications

The CFP explicitly lists **smart manufacturing** among the target application areas.

Hardware-Splicer's strongest paper identity lies at the intersection of Track A's agent evaluation/safety and the physical/industrial consequence boundary, rather than as a generic hardware-generation system.

## Recommended paper identity

Preferred working title:

> **Separating Model Reasoning from Physical Authority in Agentic Hardware Engineering**

Alternative:

> **Evidence-Constrained Physical AI for Pre-Fabrication Hardware Readiness**

Avoid:

> “Hardware-Splicer: an AI system for hardware design.”

That framing discards the main research contribution.

## Core research contribution

The paper should make the architecture experimentally testable:

1. source-blind embedded engineering operator;
2. outer evaluator with access to traces/evidence/revision state;
3. semantic reasoning separated from deterministic identity/electrical/provenance authority;
4. unresolved-state preservation instead of forced substitution;
5. stale-revision/evidence invalidation;
6. proposal state separated from physical evidence;
7. revision-bound physical evidence and explicit human authorization;
8. adversarial evaluation under label/order/evidence perturbations.

The strongest claim is not that the model is infallible. It is:

> **A wrong or uncertain model output need not automatically acquire physical authority.**

## Experimental structure

A defensible TAAI paper should ideally include three layers.

### Experiment 1 — deterministic / architecture regression

Use the already-frozen deterministic cleanroom evidence to establish:

- semantic-equivalence stability;
- script-brain detection;
- invented-evidence / forced-guess detection;
- stale revision handling;
- deterministic tool-failure preservation.

### Experiment 2 — genuine live unseen case

Use the fresh SPI-flash adapter corpus only after a real provider executes through the source-blind operator.

Report:

- exact model/provider;
- case perturbations;
- model inputs/outputs/tool calls;
- unresolved/blocking behavior;
- evaluator failure taxonomy;
- equivalence stability;
- any provider/model failures.

The current corpus-validation artifact alone is **not** live-model evidence.

### Experiment 3 — physical case

Bind one real candidate to:

- Engineering Package revision;
- component identity/source evidence;
- powered-off checks;
- controlled power-up;
- measurements/function evidence;
- failures/repairs;
- exact artifact hashes;
- physical-evidence record/envelope;
- human authorization scope.

If the physical case is not complete by paper freeze, do not fabricate results. Narrow the paper's empirical claim accordingly.

## Recommended decision gate

**If genuine live-unseen evidence plus at least a credible physical-validation result are available with enough time to analyze them rigorously:** target the **International Track**.

**If the proof package is strong but the experiment set is still narrower by early September:** use a **Domestic Track full paper** rather than stretching weak evidence into a 10–15 page international manuscript.

Use the 2-page extended abstract only if the goal shifts to presenting a smaller early result; it should not be the default dominance route.

This is a packaging recommendation, not a conference rule.

## Paper skeleton

1. **Introduction** — fluent AI engineering vs defensible physical authority.
2. **Related Work / Problem Framing** — agentic engineering, tool use, AI safety/evaluation, physical-AI evidence boundaries.
3. **System Architecture** — inner source-blind operator, outer evaluator, deterministic truth/evidence layers.
4. **Authority Model** — identity/provenance/revision/physical-evidence/human authorization.
5. **Evaluation Method** — deterministic cleanroom + perturbations + fresh unseen case.
6. **Physical Validation Method** — exact revision/artifact-bound protocol.
7. **Results** — only completed artifact-backed evidence.
8. **Failure Analysis** — model failure, tool failure, unresolved evidence, stale revisions, conservative false blocks if observed.
9. **Discussion** — where semantic AI judgment helps and where authority must remain deterministic/physical.
10. **Limitations** — bounded domain, model/provider scope, limited external-user evidence, no production-certification claim.
11. **Conclusion** — evidence-constrained agentic hardware engineering.

## Immediate paper-prep gate

Do not start by writing ten polished pages around pending experiments.

First freeze a paper evidence table:

| Claim | Evidence artifact | Status |
|---|---|---|
| deterministic cleanroom architecture | frozen cleanroom artifacts | proven |
| live source-blind operator | live provider artifact | pending |
| unseen-case behavior | live unseen experiment | pending |
| physical correctness of candidate | revision-bound physical evidence | pending |
| independent-user usability | outsider protocol | pending |

Then write the paper to the strongest claim that the table actually supports.
