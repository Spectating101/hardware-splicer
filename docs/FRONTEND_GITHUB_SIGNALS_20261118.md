# Where hardware interfaces are heading

**Research snapshot, 18 November 2026.** Hardware Splicer (HS) aims to reduce the engineering hours needed to adapt a machine to exact bought or recovered parts. The browser decision to test is whether someone can choose a replacement and understand the consequences in one project. Geometry, a bill of materials, and chat each answer only part of that question.

## What changed the recommendation

A missing BOM row is a plausible entry into engineering work. Give it an action to find another seller of the same part or evaluate a different part. Those routes require different checks. The academic evidence also supports multiple starting points. In the ecoEDA design study, seven participants started with an idea and four drew inspiration from available components. Five asked for more control over when suggestions appeared. The sample comprised 12 engineering-course students working on schematics. Transfer to mechanical design or purchasing remains a hypothesis. ## Recommended browser flow

1. **Projects.** Resume the last decision or begin with a build goal, parts list, donor, or existing design. A missing part can be recorded before CAD exists.
2. **Parts and sourcing.** For a selected requirement, compare the exact part at another seller, a candidate substitute, and a recovered unit. Show MPN, country/currency, quantity, offer date and source where known. Keep inventory on hand separate from an offer. Ask for the one missing detail that could change the choice.
3. **Review change.** Keep the current design alongside the proposed one. Show which parts are retained, which need rework, which requirements change, and which checks are stale or unresolved. Keep the agent's proposal editable and scoped to the selected item. Count hours spent obtaining evidence and redesigning wherever measured; label estimates and unknowns.
4. **Inspect and decide.** A mounting issue opens the relevant geometry. A connector question opens the connection and source. A runtime result opens its calculation and assumptions. Record the user's decision, source IDs and revision together. Where mappings are absent, offer the underlying file and say what remains unlinked.

**First integration candidate.** HS already exercised akcli on a real SPI adapter and stored a kdif visual comparison for a controlled silkscreen edit. Surface the existing inspection and diff from the review, preserving their engineering scope. That evidence demonstrates artifact delivery; it does not validate an electrical substitution. [Executed HS record](../evidence/github_signals/workshop_task_router_20261105/README.md)

**First two acceptance cases.** Use the FieldDeck display change with known runtime, changed enclosure files and unresolved generic pin/voltage checks. Pair it with an unavailable robot servo using the public sourcing question, without inventing a compatible substitute. Compare the change-review workflow with the current library/parts-file/viewer workflow. Give each the same documents and no private data. Measure elapsed engineering time to a justified decision, overlooked dependent changes, and unsupported compatibility claims. A correct result may be “need the voltage or connector evidence before deciding.” An advantage on FieldDeck alone could be overfitting the demo. [FieldDeck record](status/generated/fielddeck-display-swap-20261118.json) · [Robot sourcing case](https://github.com/TheRobotStudio/SO-ARM100/issues/161)

## The competing explanation

Claude Opus 5.5 reviewed the evidence summary and raised a product risk: an engineer could keep inventory in InvenTree or Part-DB, launch a specialist check in an existing editor, and never need a new full-time workspace. The GitHub requests demonstrate friction with sourcing and locating parts. They leave demand for a separate browser product open. Test the same change review opened directly from a BOM row against opening it from the HS project home. An illustrative internal hurdle is to halve median engineer-minutes across ten real stuck-part cases with no increase in unsupported approvals. That is a proposed business threshold, not a measured result. Preserve “insufficient evidence” as a valid outcome. Track the one-time work of preparing each case separately so a fast preset cannot hide high engineering setup costs.
