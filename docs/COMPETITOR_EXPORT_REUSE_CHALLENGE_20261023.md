# Compete and absorb — real cross-tool interchange challenge

HS does **not** concede the market to existing AI hardware engineering generators. But it must use their documented user-owned exports, open-source tooling, and transparent interoperability where legitimate, rather than wish for partnership APIs.

## Formats we can legitimately work with

- **Flux** (official documented exports): schematic EDIF netlist, layout IPC-D-356, BOM CSV, STEP/STL, Gerbers, pick/place CSV and native FLX. Current HS supports BOM CSV, local STL structural review and reference STEP through the experimental project UI; **not** an automatic FLX/EDIF/D356 or project-native import. Source: https://docs.flux.ai/reference/data-portability and https://docs.flux.ai/faq/faq-s-about-the-pcb-editor .
- **tscircuit**: Circuit JSON generated by actual open-source engine. This was the successful four-component software interchange probe earlier in the stack. https://docs.tscircuit.com/ .
- **KiCad**: open, local schematics and PCB. The MIT open-source `kicad-to-circuit-json` converter offers a path into the already existing HS Circuit JSON review. Not guaranteed to preserve every source net, hierarchy, constraint or fab attribute. https://github.com/tscircuit/kicad-to-circuit-json .
- **Cirkit Designer**: simulation/firmware strengths; need authorized export from a real project before claiming interchange. https://www.cirkitdesigner.com/ .
- **Schemr**: public browse worked; generating and obtaining owned source artifacts remains account-gated. No verified public generator API.

## Live results — do not misrepresent

Tested `hardware/reference_designs/spi_flash_adapter_v1/spi_flash_adapter_v1.kicad_sch` using real `kicad-to-circuit-json@0.0.144` (with separately installed peer libraries). Converter produced **679 Circuit JSON documents**: 40 source components, 83 source ports, 16 source nets, 87 legacy schematic traces. It reported **zero converter warnings**.

Posting the genuine output to **HS `POST /v1/interchange/circuit-json/inspect`** returned HTTP 200 and **40 imported components** but **0 imported nets**, `status=blocked`, `compilable=false`. HS's existing importer does not correctly reconstruct the converter's net/trace dialect. *That is not a successful HS integration.* It is a precise reproducible interoperability defect we should fix, benchmark and potentially upstream to the converter before claiming reuse. A superficial HTTP 200 must not be counted as success.

The example scripts in `examples/integrations/kicad-circuit-json/` reproduce the conversion and enforce a FAIL outcome when connectivity disappears. No phantom circuits are synthesized and no external KiCad files executed.

## Competitive experiment, not a promise

1. Fix converter→HS preservation of actual source nets and terminal connectivity, requiring 40→40 component retention **and nonzero grounded multi-pin net retention** for the real SPI-flash fixture; confirm against KiCad's own exported netlist as the independent connectivity oracle.
2. Submit the same donor-rover and greenfield ESP32 design to HS plus at least one competitor with authorized output. Compare their actual files, not features on marketing pages.
3. For each, score BOM quantities, valid netlist connectivity, power constraints, firmware build, CAD geometry and human interventions; use reproducible artifact receipts.
4. Improve HS by adopting strong external functions and standards rather than duplicating open-source EDA or proprietary UI.
5. Use physical low-voltage measurement gates before any build-ready claim.

**Rule:** A tool is worth integrating only when the complete workflow benefits. Conversion record counts alone do not imply a viable electrical design.
